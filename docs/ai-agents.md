# AI エージェントと開発する

このブログは AI エージェント（Claude Code・Cursor・Codex など）と一緒に開発し、記事も書きます。このページは、エージェントが何を読み、どう動くかをまとめたものです。

## エージェントが読むファイル

| ファイル                                | 役割                                                                        |
| --------------------------------------- | --------------------------------------------------------------------------- |
| `CLAUDE.md`                             | Claude Code の入口。`AGENTS.md` と `rules/*.md` を読み込むだけ              |
| `AGENTS.md`                             | どのエージェントにも共通の作業ガイド（コマンド・まず読むもの・守ること）    |
| `rules/*.md`                            | 設計のルール。雛形ができたら、守れているかを検査やテストで確かめる          |
| `.cursor/rules/*.mdc`                   | Cursor 向けの入口。本文は `rules/*.md` を指すだけ                           |
| `.cursor/skills/*/SKILL.md`             | 手順をまとめたスキル（正本）。`.claude/skills` はここへのシンボリックリンク |
| `docs/improvement/backlog.md`・`log.md` | 改善候補と、直したことの記録                                                |
| `docs/decisions/`                       | 判断の理由（ADR）                                                           |
| `docs/specs/`                           | 実装前に書いた指示書                                                        |

## スキル

| スキル                 | 使うとき                                                   |
| ---------------------- | ---------------------------------------------------------- |
| `improve`              | 改善を 1 件回す（バックログから選ぶ・会話の指摘を直す）    |
| `write-spec`           | 機能を足す・大きく変える前に、`docs/specs/` に指示書を書く |
| `write-post`           | 記事を書く・直す・移行した記事を整える                     |
| `conventional-commits` | コミットメッセージを書く                                   |

## エージェントに任せるときの進め方

1. **頼む**: 直したいこと、または「バックログから 1 件」と伝える。大きな機能は先に指示書（`docs/specs/`）を書かせてレビューする
2. **直させる**: エージェントは `improve` スキルに沿って、関連する ADR とルールを読んでから直す
3. **再発を防がせる**: 直しただけで終わらせず、検査・テスト・ルール・スキルのどれかを足させる（[改善ループ](./improvement-loop.md) の「再発を防ぐ」）
4. **記録させる**: `docs/improvement/log.md` に 1 行、方針を変えたら ADR を 1 つ
5. **確かめる**: PR の CI が通ることと、Workers Builds のプレビュー URL で見た目・構造化データを見る

## npm に届かない環境で作業するとき

エージェントの作業環境によっては、npm のレジストリに接続できず `make setup` もビルドもできない。そのときは次のように進める。

- **フォーマット**: Oxfmt の単体のバイナリを GitHub Releases（`oxc-project/oxc` の `oxfmt_v<版>`）から取り、`oxfmt .` で直す。版は `vite-plus` が使うもの（`vp check` と同じ結果になる版）にそろえる
- **検査・テスト・ビルド**: PR を出し、GitHub Actions の CI に回してもらう
- **依存を足す・上げる**: `package.json` を直して PR に push すると、Lockfile ワークフローが `pnpm install --lockfile-only` で `pnpm-lock.yaml` を作り直し、PR のブランチにコミットする。最初の CI はロックファイルが古いので失敗してよい。ボットのコミットで動く CI は承認待ち（`action_required`）になるので、`gh api -X POST repos/<owner>/<repo>/actions/runs/<run id>/approve` で承認する。手元のブランチは `git pull` でボットのコミットを取り込む
- **CI の結果を読む**: ログ本体を開けない環境でも、失敗した手順の出力の末尾が注釈に出る（`scripts/ci-step.sh`）。`gh api repos/<owner>/<repo>/check-runs/<job id>/annotations` で読む
- **見た目を確かめる**: 見た目に関わる PR では、Screenshots ワークフローが主なページを PC とスマホで撮り、`screenshots/<ブランチ名>` ブランチに置く（PR にもコメントする）。`git clone --depth 1 -b screenshots/<ブランチ名> <リポジトリ>` で取って画像を開く。直したらもう一度撮って見比べる

## 指摘の伝え方

会話で指摘するときは、「何がどう困るか」を書くと再発防止まで届きやすくなります（例:「リンクカードが読み込み後にずれて、本文が跳ねる」）。
エージェントは指摘を `log.md` に残し、同じ種類の指摘が続いたらルール文書か検査に格上げします。
